## 一、项目背景与目标

用户使用 **草料二维码** 平台管理工厂安全设备（灭火器、急救药箱、应急灯、洗眼器、压力表、消防气瓶等），数据分散在平台各码、各表单中，无法集中分析。目标：

1. 把草料平台数据汇聚成**实时**分析看板；
2. 团队可随时通过浏览器访问；
3. 覆盖设备状态、效期预警、计划执行等多维度分析。

最终交付：一个直连草料官方数据库、实时反映最新数据的 Web 看板，部署在云端（Railway），团队任意设备浏览器访问。

## 三、踩过的坑与解法（价值最高部分）

### 坑 1：草料数据模型混淆（template 主数据表 vs table 表单日志）
- **现象**：急救药箱碘伏看板显示 2025-10-04（已过期 296 天），草料前台却是 2027-03-01。
- **根因**：`template_codeinfo_*` 是"子码主数据表"，存的是**码当前字段值**（草料前台展示的就是它）；`table_dXX` 只是**表单提交历史日志**，可能是建箱时一次旧提交，不代表当前状态。旧代码误读了 `table_d24`。
- **解法**：`/api/first-aid/expiry` 改读 `template_codeinfo_d25`；日期解析兼容 `YYYY/MM/DD` 与 `YYYY年MM月DD日`；修 UTC 时区导致的显示偏移一天。
- **经验**：分析"当前状态"必须认准 template 主数据表；不确定时用 `information_schema` 搜列名定位权威表。

### 坑 2：前端整段失效（一行废代码）
- **现象**：数据库状态徽章"检测中"永久转圈。
- **根因**：主 `<script>` 末尾残留一行 `}  }).join('');` 废代码，导致**整个脚本解析失败、完全不执行**，`loadHealth()` 从未被调用。
- **解法**：抽取 `<script>` 块用 `node --check` 定位到具体行，删除后复测通过。
- **经验**：大文件多处 Edit 后，务必用 `node --check` 复核前端脚本语法，避免"整段不执行"类隐性故障。

### 坑 3：沙箱网络拦截 git 推送
- **现象**：`git push`/`git fetch` 到 github.com:443 偶发 `Connection was reset` 或连接超时；`git ls-remote` 有时却通，极具迷惑性。
- **解法**：改用 **GitHub REST Contents API**（小 HTTPS 请求，`api.github.com` 在沙箱内可达）：`GET /contents/{path}` 拿 sha → `PUT` 同路径（body 含 base64 内容 + sha）逐文件提交。两次提交均 HTTP 200，Railway 自动重部署成功。
- **经验**：沙箱里 git 大传输被拦时，优先用 GitHub API 推小文件；大仓/多文件仍需解决网络出口。

### 坑 4：GitHub push 误判成功
- **现象**：推送重试循环靠 `grep "main -> main"` 判断成功，实际没推上去，GitHub HEAD 停在旧 commit。
- **解法**：用 `gh api repos/.../commits/main --jq '.sha'` 校验远端 HEAD 是否等于目标 commit SHA。后续统一以"远端 SHA 比对"为唯一判据。

### 坑 5：时区偏移
- **现象**：日期显示比实际差一天。
- **根因**：UTC 解析致偏移。
- **解法**：用本地年月日拼 ISO，避免 UTC 转换。

### 坑 6：`query()` 返回的是行数组，不能直接解构取"整表"
- **现象**：应急灯多维度接口首版返回 `total=0`、`byDevice` 只是首行对象而非数组，图表维度数全错。
- **根因**：本项目的 `query()` 封装直接 `return rows`（**数组**），而首版代码写成 `const [byDevice] = await query(...)`，把"第一行"当成了"整张结果集"。
- **解法**：聚合类查询用 `const byDevice = await query(...)`（拿到完整数组），仅 `SELECT COUNT(*)` 这类单行结果才用 `const [row] = await query(...)`。
- **经验**：封装返回数组的查询函数，对"期望多行"的查询**不要**用数组解构；不确定返回结构时先用 `node -e` 直连打印验证再写前端。

## 四、做得好的地方

- **架构选择正确**：坚持"直连官方库实时查询"，天然实时、无同步滞后（详见技术文档与用户问答）。
- **每次修复都线上复测**：所有 bug 修复后都在 Railway 实测 API 返回 200、数据正确，不靠"本地能跑"臆断。
- **把隐性需求当硬指标**：用户提的"数据要跟草料一致""超期只显示最新周期"都作为验收标准落实并验证。
- **前端健壮性演进**：从会永久卡死的 `Promise.all` 演进到 `allSettled + 超时 + finally` 兜底 + no-cache，可用性显著提升。
